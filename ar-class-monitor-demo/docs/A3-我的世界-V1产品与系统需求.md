## 〇、关键架构决策（硬约束，源自现有代码）

以下 5 条是现有系统的真实架构边界，不是建议项，任何实现不得违反：

### 0.1 编号显示规则

《我的世界》内部使用 `course=3`（现有编号 `0/1/2/4`，3 空缺，内部补位）。

- "A3"、"第三环节"等内部编号**只能出现**在：教师端、文件名、配置、代码、日志。
- 学生端和大屏端**不得显示**任何内部编号，只显示：

  ```
  《我的世界》
  ```

- 必须检查所有标题、按钮、加载状态、空状态和大屏文案。

### 0.2 学生端投送机制（不新建推送系统）

当前系统**不存在**"向学生推送路由页面"的独立机制（`student_view_changed` 不存在，也不要新建）。

学生页面切换必须映射到现有机制：

- `/api/lesson`
- `task_push`
- `feed`
- 课程和任务解锁
- 学生端固定工作台 pane（`student/index.html` 的固定四 pane）

允许在现有 lesson/task 数据中新增一个**可选字段** `student_view`：

```json
{
  "course": 3,
  "task": "world_create",
  "student_view": "world_create",
  "bigscreen_block": "world_scene"
}
```

学生端收到状态后，只切换固定工作台内的功能 pane，**不创建独立路由系统 / 消息通道**。

### 0.3 事件协议（统一为现有格式）

沿用全系统事件结构（`server.py` `POST /api/collect` → `agent-live/events.jsonl`）：

```json
{
  "ts": 1786725296249,
  "sid": "student-82",
  "event": "life_submitted",
  "payload": {
    "worldId": "world-01",
    "roundId": "round-01",
    "lifeId": "life-104",
    "version": 1
  }
}
```

**不引入** `{eventId,type,sessionId,roundId,timestamp,payload}` 第二套事件结构。
`worldId`/`roundId`/`lifeId`/`version` 等扩展信息放 `payload`。
`sid` 语义与生成方式沿用 `lib/track.js` 现有实现（URL 参数 → localStorage → 随机匿名，与签到号对齐），不建立第二套学生身份。

### 0.4 世界引擎独立于 `server.py`

《我的世界》需要服务端持续模拟，学生关页面/断网后生命必须继续运行。

世界引擎**不得**直接塞进 `server.py` 的请求处理循环。V1 参考 `water-analyzer.py` 的后台进程模式，设计为独立进程 `world-engine.py`：

```text
events.jsonl
↓
world-engine.py 读取新增事件和教师控制状态
↓
推进世界模拟
↓
原子写入 world-state.json
↓
server.py 暴露只读状态接口
↓
bigscreen / student 定时轮询
```

V1 不强制引入 WebSocket。

### 0.5 AI 讨论（复用现有 AI 接入模式）

AI 讨论复用 `water-analyzer.py` 的接入模式：

- 服务端读环境变量 `DEEPSEEK_API_KEY` 或本地 `.deepseek_key`；
- API 密钥不得发送到学生端；
- 有 AI 能力时生成解释和规则建议；AI 不可用时规则回退；
- AI 只能解释、转换、预测；**不能**自动替学生提交生命规则；
- AI 回答必须优先用该学生生命的真实运行数据；数据不足必须明确说明，不能编造运行原因。

# 1. 项目定义

《我的世界》是一个由教师端、大屏端、学生端共同参与的数字社会世界。

每位学生通过学生端创造一个数字生命，并将生命发布到大屏上的公共世界中。生命进入世界后，不由学生直接操纵，而是根据学生设计的规则自主行动。

世界持续运行，生命会：

- 移动；
- 消耗和获得能量；
- 寻找资源；
- 遇到事件；
- 与其他生命互动；
- 建立或破坏关系；
- 形成群体；
- 因学生修改规则而改变行为。

产品核心体验是：

```text
学生产生想法
↓
创造生命
↓
生命进入公共世界
↓
世界真实运行
↓
学生观察结果
↓
学生提出修改
↓
生命使用新规则再次运行
↓
学生比较修改前后的变化
```

核心目标不是让学生完成一次作品，而是让学生感受到：

> 我创造的生命进入了共同世界，并且我的规则真的改变了它和世界。

# 2. 三端职责

## 2.1 教师端

教师端负责控制课堂进程，不直接控制单个生命。

教师可以：

- 进入《我的世界》教学场景；
- 控制大屏当前显示的页面；
- 向学生端推送对应操作页面；
- 开始、暂停和继续世界；
- 开始一个创作轮次；
- 截止学生提交；
- 批量发布学生生命；
- 开始观察；
- 触发预设公共事件；
- 开始修改轮次；
- 应用学生提交的新版本；
- 查看连接人数和提交进度；
- 选择一个生命在大屏上聚焦展示；
- 结束本轮并展示结果。

教师不能：

- 直接替学生修改生命；
- 在世界运行过程中任意给某个生命增加能量；
- 直接指定某个生命攻击或帮助另一个生命；
- 临时修改底层世界规则；
- 在没有提示的情况下改变实验条件。

## 2.2 大屏端

大屏端显示所有人共享的公共世界。

大屏不是操作后台，也不是数据报表。它首先应该是一个一直运行、可以观察的数字生态。

大屏负责显示：

- 世界环境；
- 所有已发布生命；
- 生命移动和状态；
- 资源；
- 世界事件；
- 生命之间的互动；
- 关系连接；
- 群体聚集；
- 公共事件；
- 当前课堂阶段；
- 学生生命加入世界的过程；
- 被教师选中的生命详情。

大屏不显示：

- 学生的完整编辑表单；
- 复杂后台参数；
- 所有底层日志；
- 教师管理按钮；
- 学生隐私信息；
- AI对话全文。

## 2.3 学生端

学生端是学生的个人创造站和观察站（固定工作台内挂载，见 §8）。

学生可以：

- 接收教师推送的页面；
- 创建自己的生命；
- 设置外形和颜色；
- 选择性格倾向；
- 选择移动偏好；
- 设计一个核心能力；
- 为能力设置触发条件；
- 理解能力代价；
- 将生命提交到公共世界；
- 查看自己的生命状态；
- 查看与自己有关的关键事件；
- 与AI讨论运行结果；
- 修改生命规则；
- 提交一个新版本；
- 比较修改前后的结果。

学生不能：

- 使用摇杆直接控制生命；
- 任意拖动生命位置；
- 直接生成资源；
- 直接修改能量；
- 操作其他学生的生命；
- 查看其他学生的完整规则；
- 绕过能力代价；
- 在世界运行中即时反复修改规则。

# 3. 课堂状态机

整个功能必须按照明确状态运行（映射到现有 `/api/lesson` + `task_push` 机制，见 §4）。

```text
未进入场景
↓
场景准备
↓
学生创造生命
↓
等待提交
↓
生命批量进入世界
↓
世界运行
↓
观察与讨论
↓
学生修改生命
↓
应用新版本
↓
再次运行
↓
结果比较
↓
结束或继续下一轮
```

状态枚举：

```text
IDLE
PREPARING
CREATING
SUBMITTING
PUBLISHING
RUNNING
OBSERVING
REVISING
APPLYING
COMPARING
FINISHED
```

每个端根据同一个课堂状态显示不同页面。

| 课堂状态 | 教师端 | 大屏端 | 学生端 |
|---|---|---|---|
| PREPARING | 检查连接 | 世界等待画面 | 等待教师 |
| CREATING | 查看创作进度 | 空世界或孵化区 | 创建生命 |
| SUBMITTING | 截止和审核 | 显示提交数量 | 确认提交 |
| PUBLISHING | 发布生命 | 生命进入世界 | 显示发布结果 |
| RUNNING | 控制运行 | 完整世界 | 观察自己的生命 |
| OBSERVING | 选择案例 | 聚焦生命和事件 | 查看原因和动态 |
| REVISING | 查看修改进度 | 世界暂停或继续观察 | 修改规则 |
| APPLYING | 应用版本 | 显示生命更新 | 等待应用 |
| COMPARING | 展示结果 | 前后变化 | 查看个人结果 |

# 4. 教师"下一页"的准确行为（对接现有课程机制）

> **技术定义（硬约束 0.2）**：教师点击"下一页"时，**不是在课堂现场临时生成代码**，而是激活一个预先实现好的《我的世界》场景，并把对应的学生操作页面推送给学生端——通过改变现有课程/任务状态实现，学生工作台切换到对应 pane。

教师点击"下一页"：

```text
教师当前页面：我的世界·介绍（教师端）
点击下一页
↓
课堂状态变为 PREPARING（对应现有 lesson/task 状态推进）
↓
大屏切换为《我的世界》公共场景（大屏 block 激活 world_scene）
↓
学生端任务 pane 显示"世界即将开放"
↓
世界引擎加载本节课配置
↓
加载完成后教师可以点击"开始创造"
```

教师点击"开始创造"：

```text
课堂状态变为 CREATING
↓
学生端收到 student_view=world_create（工作台切换到创建生命 pane）
↓
大屏显示空世界和实时提交数量
↓
教师端显示学生完成进度
```

"推送页面"定义为：

> 教师改变课堂状态（现有 `/api/lesson` + `task_push`），学生端根据服务端下发的 `student_view` 字段，在**固定工作台内**自动切换到预先实现好的功能 pane。

建议的 lesson/task 扩展字段：

```json
{
  "course": 3,
  "task": "world_create",
  "student_view": "world_create",
  "bigscreen_block": "world_scene"
}
```

# 5. 公共世界的组成

公共世界中包含四类主要对象：

## 5.1 生命

每个生命至少包含：

```text
身份
外观
位置
速度
能量
状态
性格倾向
行为规则
核心能力
能力代价
关系
版本
所属学生
```

建议数据结构（存 world-state.json，见 §11）：

```json
{
  "lifeId": "life-104",
  "ownerId": "student-82",
  "name": "小灯",
  "version": 1,
  "appearance": {
    "shape": "spark",
    "primaryColor": "#F3C84B",
    "secondaryColor": "#FFFFFF"
  },
  "traits": {
    "sociability": 70,
    "curiosity": 55,
    "caution": 40,
    "generosity": 75
  },
  "energy": 80,
  "maxEnergy": 100,
  "state": "exploring",
  "ability": {
    "type": "restore_energy",
    "trigger": "nearby_life_energy_below_30",
    "cost": 8,
    "cooldown": 60
  }
}
```

## 5.2 资源

资源是生命获得能量或能力材料的主要来源。

资源规则：

- 资源在不同区域动态产生；
- 资源有存在时间；
- 资源被获取后消失；
- 资源不能无限供应；
- 同一区域资源过多时，生成速度降低；
- 长期缺少生命的区域可增加资源；
- 多个生命争夺同一资源时，由距离、速度和行为规则决定结果。

V1可以只保留一种通用能量资源，避免系统过早复杂化。

## 5.3 世界事件

事件分为：

| 类型 | 作用 |
|---|---|
| 机会事件 | 提供特殊收益 |
| 资源事件 | 产生一批资源 |
| 危险事件 | 消耗能量或改变移动 |
| 信息事件 | 改变生命对区域的判断 |
| 公共事件 | 同时影响多个生命 |

V1至少实现三个事件：

1. **能量雨**：区域内产生大量资源；
2. **能量潮汐**：资源向世界某一侧集中；
3. **危险波动**：某个区域持续消耗生命能量。

事件必须有：

```text
出现
持续
影响
减弱
结束
```

五个阶段。

## 5.4 世界区域

V1建议使用四个区域：

| 区域 | 主要作用 |
|---|---|
| 安全区 | 能量消耗较低 |
| 资源区 | 资源产生概率较高 |
| 危险区 | 持续消耗能量 |
| 未知区 | 可能触发隐藏事件 |

区域可以有视觉差异，但不能使用过强遮罩影响观察生命。

# 6. 世界核心规则

## 6.1 能量系统

所有生命都有能量。

能量变化来源：

```text
移动：消耗能量
使用能力：消耗能量
进入危险区：消耗能量
获得资源：增加能量
接受帮助：增加能量
受到攻击：失去能量
休息：缓慢恢复或降低消耗
```

建议V1初始规则：

```text
初始能量：80
最大能量：100
移动消耗：低速持续消耗
能力消耗：由能力配置决定
低能量阈值：30
休眠阈值：0
```

课堂产品不建议让生命永久死亡。

能量归零后建议进入：

```text
休眠状态
```

休眠生命：

- 暂停移动；
- 可以被其他生命帮助；
- 可以被资源事件唤醒；
- 仍然保留在世界中；
- 学生可以观察其休眠原因。

这样既保留行动代价，也避免学生过早失去参与感。

## 6.2 移动决策

生命每次决策时，根据以下因素选择目标：

```text
自身能量
性格倾向
附近资源
附近危险
附近生命
已有关系
核心能力
区域偏好
当前事件
```

行为优先级示例：

```text
能量极低 → 优先寻找资源或休息
附近存在危险 → 根据谨慎程度决定逃离
附近生命需要帮助 → 根据慷慨程度和能量决定是否帮助
附近有资源 → 根据好奇和资源偏好决定靠近
存在强关系生命 → 根据社交倾向决定靠近
没有紧急目标 → 探索或游荡
```

每次决策必须记录"原因"，供学生端显示。

例如：

```json
{
  "action": "move_to_resource",
  "reasonCode": "LOW_ENERGY_NEARBY_RESOURCE",
  "reasonText": "能量较低，附近发现了资源"
}
```

## 6.3 生命与生命相遇

两个生命进入互动距离后，不是自动发生同一种行为。

系统根据双方规则决定：

- 忽略；
- 靠近；
- 回避；
- 帮助；
- 分享；
- 连接；
- 竞争；
- 攻击。

一次相遇至少记录：

```text
相遇时间
双方生命
相遇前状态
双方关系
触发行为
能量变化
关系变化
位置变化
行为原因
```

## 6.4 关系系统

任意两个生命之间存在关系值。

建议V1范围：

```text
-100 至 +100
```

关系阶段：

```text
-100 至 -30：对立
-29 至 9：陌生或疏离
10 至 29：熟悉
30 至 59：连接
60 至 100：强关系
```

关系变化示例：

```text
普通相遇：小幅增加熟悉度
帮助：关系增加
分享：关系增加
合作：双方关系增加
攻击：关系下降
争夺资源：关系下降
长期未相遇：关系缓慢回归中性
```

关系必须真正影响后续行为，例如：

- 正向关系提高再次靠近概率；
- 正向关系提高帮助和分享概率；
- 负向关系提高回避或竞争概率；
- 强关系生命可能形成短时群体移动。

不能只记录关系数值而不让关系参与决策。

## 6.5 能力与代价

每个生命V1只允许一个核心能力。

建议第一版能力：

| 能力 | 效果 | 代价 |
|---|---|---|
| 恢复 | 为附近生命恢复能量 | 自身消耗能量 |
| 照亮 | 暂时显示隐藏资源 | 移动速度降低 |
| 连接 | 提高两个生命建立关系的概率 | 暂停移动 |
| 探测 | 提前发现危险或资源 | 持续消耗能量 |
| 防护 | 降低危险事件影响 | 无法同时获取资源 |

能力必须包含：

```text
触发条件
作用对象
产生效果
自身代价
冷却时间
使用限制
```

不能出现没有代价、可以无限使用的能力。

## 6.6 世界平衡

后台持续监控：

- 世界总能量；
- 平均能量；
- 活跃生命数量；
- 休眠生命数量；
- 资源密度；
- 事件密度；
- 生命聚集程度；
- 互动频率；
- 帮助和攻击比例。

V1平衡规则：

```text
平均能量过低 → 提高资源生成率
休眠生命过多 → 触发小型能量事件
资源过多 → 降低资源生成率
生命过度聚集 → 在其他区域增加机会
长期没有互动 → 适度调整资源分布
事件过于频繁 → 降低事件生成率
```

自动平衡必须有上下限，避免系统频繁震荡。

# 7. 大屏画面设计

大屏建议采用：

```text
左侧信息栏 + 中央世界 + 右侧动态栏
```

## 8.4 AI互动页面

AI只承担三种职责：

### 把想法转换成规则

学生输入：

```text
我希望它帮助别人，但不要把自己耗尽。
```

AI转换：

```text
当自己的能量高于45，
并且附近生命能量低于30时，
使用恢复能力；
每次消耗8点能量；
60秒内最多使用一次。
```

### 解释运行结果

学生提问：

```text
为什么我的生命休眠了？
```

AI基于真实日志回答：

```text
它连续帮助了3个生命，共消耗24点能量。
随后进入危险区，又失去12点能量。
因为没有触发寻找资源规则，所以最终进入休眠。
```

### 帮助提出假设

```text
如果把帮助条件从能量高于30改为高于50，
它可能减少帮助次数，但更容易保持行动能力。
```

AI不能自动提交修改，最终必须由学生确认。

> 实现约束（硬约束 0.5）：AI 讨论由服务端（参考 `water-analyzer.py`）完成，读 `.deepseek_key`，密钥不下发；AI 失败规则回退；必须基于该学生真实运行数据，数据不足必须明说。

# 11. 世界状态文件初步结构（world-state.json）

V1 快照。**浏览器不得直接依赖文件路径读取**，必须由 `server.py` 提供按角色裁剪后的只读接口。

```json
{
  "updated_at": 1786725296249,
  "world_id": "world-01",
  "course": 3,
  "lesson_state": "RUNNING",
  "round_id": "round-01",
  "simulation_time": 243.5,
  "engine": {
    "status": "running",
    "version": "world-engine-v1",
    "last_event_offset": 12894
  },
  "summary": {
    "total_lives": 28,
    "active_lives": 24,
    "sleeping_lives": 4,
    "average_energy": 63
  },
  "lives": [],
  "resources": [],
  "public_events": [],
  "relationships": [],
  "key_events": []
}
```

按角色裁剪的接口要求（硬约束）：

- 学生端：只能读到**自己的**生命详情 + 公开世界概览（不能看其他学生的完整规则）；
- 大屏：只读公共可视状态；
- 教师端：可读管理和统计状态。

**不要只依赖前端隐藏敏感字段，服务端必须按角色裁剪**（worldId/roundId/lifeId/version 在 payload 中，学生规则只在教师/学生本人视图中出现）。
